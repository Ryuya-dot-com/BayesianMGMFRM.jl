## なぜこの一件を先に行うのか

能力を測る項目が少なく、その負荷量も小さい場合、評価者の厳しさや一貫性を含むモデルの推定が難しくなる可能性がある。現在の中央付近の固定真値pilotは、人物のSDも小さい工学的な一例だった。そこで、人物をN(0,I)から生成するR0と、能力1への二つの負荷量を小さくしたR1を使い、現在の計算設定が別の入力にも接続できるかを確かめる。難しさの増加自体は仮説であり、今回生成した二つの入力を見ただけでは結論しない。

全データの2 fitは、元の入力・真値に対するパラメータ評価の接続を調べる。追加10 fitは、各条件の全5foldを訓練データだけから推定するために必要である。一部のfoldだけでは、予定した1,250評定全体のCV得点を作れない。全データfitを予測に流用して12 fitを2 fitに減らすことはしない。

SBC、代替事前、CmdStan追加fitはこの実行表に含めない。これらは別の問いであり、本リハーサルの成功で代替できない。Uchiharaを参考にした合成応用も後段の説明例として保持する。この50人・5項目・5評価者・4カテゴリーのモデルを、実際のUchiharaの設計や構成概念に対応する検証済みモデルとして説明しない。

一つの二値事象を独立Bernoulli試行とみなす単純な例でも、1／1成功の両側95%正確区間は[0.025, 1]、0／1失敗の片側95%上限は0.95となる。これらは本案の反復不足を示す算術例で、新しいfitの結果から得た成功率・被覆率ではない。全12 fitの成功数を分母12の独立二項試行と扱うこともできない。

## 計算設定・予算・停止

全12 fitでAdvancedHMC、基準raw事前、4チェーン、各warmup1,000・保持1,000を使う。初期raw座標は全128要素0、既存のjitter SD 0.1。真値を初期値に使わない。既存のstep size 0.03、target accept 0.9、最大深さ12、対角metric、ForwardDiffを継承する。設定は[入力付き計画](../../results/workflows/20260921-core-run-plan-01/proposal/bound-plan.json)へ列挙した。

| 資源 | 提案上限／扱い |
| --- | --- |
| 推定 | 各fit 1,800秒。起動・保存とその確認を含む |
| 保存fitの評価 | 各300秒。再推定とは別の処理として監視 |
| 入力・全体集計 | 各300秒 |
| 全バッチ | **28,800秒＝8時間**。逐次実行、並列jobは1 |
| 観測RSS | 所有プロセス群で8 GiB |
| 出力 | 入力・全cache・評価・ログ・scratchを合わせて**4 GiB** |
| 再実行 | 自動retry、draw延長、seed変更、失敗IDの置換は全てなし |

12×(1,800＋300)＋300＋300＝25,800秒で、全体上限との差は3,000秒である。この差は上限算術上の余裕であり、仕事を追加する予算ではない。資源監視はポーリングで、硬いOS上限ではない。

保存済み中央pilotの629.15秒とcache 146,262,522 bytesを12倍すると、約2.10時間・1.63 GiBとなる。[費用計算](../../results/workflows/20260921-core-run-plan-01/calculations.json)ではこれを単純な参考値に限定した。今回の人物母集団・負荷量・訓練行数は異なり、新しいfitの探索や評価時間を予測した値ではない。8時間・4 GiBは、完走を保証しない有限の停止予算として提案する。

事前拒否は元IDの `pre_fit_rejected` とし、予定表の残りへ進む。診断不適格・精度未解決も結果を保存し、再試行せず固定順を維持する。コマンド失敗、資源停止、観測不能などの運用上の失敗ではバッチを止め、残りを未実行として残す。現在のjobの終了が確認できなければ「未解決」であり、勝手に終了済みや再開可能とは判定しない。

終了コード0・fitの保存成功・事前検査通過のいずれも、診断通過や科学的受入の代わりにしない。全foldが揃わなければCV得点を作らず、全予定分母の欠落状態を報告する。

## 計画とworkerを接続した段階の検証

12件の事前検査は通過し、128 raw座標、人物ID、Q、明示カテゴリー、訓練／未使用行と有限の初期対数密度を確認した。R0/R1の対応foldは同一で、各条件の未使用行は重複なく1,250行を覆う。過去の別データfitは、seedだけを合わせても訓練ターゲットの違いで得点化を拒否した。

過去の固定真値fitは専用の工学検査として別に評価し、159量の平均・区間が従来結果と一致した。精度未解決を保存・再読込みして分母に残す検査には、合格済み記録を明示的に変更したfixtureを使った。過去fitの新しい精度不良を発見した結果ではない。停止理由から研究上の失敗枠への変換も手製のreceiptで検査しており、今回の12件を実際に中断した証拠ではない。

計画の6検査、ターゲット・停止・混入拒否の185検査、保存fitと精度未解決の169検査、計**360検査**が通過した。Juliaの二つの確認は115.38秒・111.58秒、最大観測RSSは約2.55 GiB。新しいMCMC・正式回復・SBC・CV再推定は全て0である。[最終検証記録](../../results/workflows/20260921-core-run-plan-01/verification.json)は本体ソース・旧成果物の不変性と未確認事項も保持する。

## 親処理と停止後集計の接続

[親処理](../../scripts/mgmfrm_core_controller.py)を追加した。固定順の12 jobについて、準備、fit、保存fitの評価、集計を既存guardへ接続し、一つの期限と出力rootを共有する。元のR0/R1入力8ファイルは同じbytesを再利用し、追加生成・引き直し・新規MCMCはいずれも0である。[現在のコードを結合した未承認計画](../../results/workflows/20260921-core-controller-01/plan/bound-plan-02.json)は、元の条件・seed・予算を維持する。コード変更前の計画と検証記録も残した。

各段階の開始記録・監視receipt・worker結果・成果物のSHA256を照合し、保存fitと得点化したfitのpath・SHA256・seedを一致させる。終了コード0だけでは採用しない。`inspect` は読み取り専用で、事前拒否、診断警告、精度不足、fit保存後の評価欠損、終了未確認を区別する。既存の実行先への再実行は拒否し、自動retryや失敗IDの置換は行わない。

運用上の失敗で停止した場合は、全予定枠のledgerを残し、そのバッチ内で別の子プロセスを起動しない。全12枠の処理が完了し期限に余裕がある場合だけ、自動集計する。停止後の明示的な `collect` は、**MCMCを呼ばない別処理**として300秒・観測RSS 8 GiB・出力2 GiBの新しい上限とreceiptを持つ。これは停止した8時間予算を延長する機能ではない。観測した終了情報がなければ、研究上は `missing_attempt` を維持し、終了や再開可能性を推測しない。

[親処理の12テスト](../../test/mgmfrm_core_controller.py)では、自分で起動した短いPython workerにより、期限・容量停止、SIGTERM、非ゼロ終了、評価失敗、欠損／破損結果、異なるID、親処理の記録欠落、成果物変更を検査した。全枠の正常な処理経路でも事前拒否・精度不足・診断警告を保持し、全フェーズの期限と容量上限の共有を確認した。このfixtureのfitファイルはダミーで、推定の証拠ではない。

実際のJulia集計への接続では、失敗1・未実行11の記録と、手製の精度不足1・失敗1・未実行10の記録を用いた。いずれも各条件159量の予定分母を1に保ち、適格0、全5fold未完了、CV得点なし、対応差の反復MCSEなしとなる。精度不足fixtureには推定値を入れていない。過去の実fitを用いた174チェックと12ターゲットの185チェックも通過した。誤ったID・成果物ハッシュ・別fitへの参照は[集計検査](../../test/mgmfrm_core_collection.jl)で拒否する。[最終検証記録](../../results/workflows/20260921-core-controller-01/verification.json)に内訳と限界を保存する。

**実際の12 fit連続実行、正式なCV再推定、独立科学レビューは未実施である。** 短い子プロセスでの停止試験は、8時間の実MCMC完走や瞬間的な資源ピークの捕捉、SIGKILL後のcleanupを保証しない。コード・入力の不変性確認も、統計的妥当性や全体CIの代替ではない。
