# A0の焦点量の精度評価と実行中の資源監視

更新：2026-09-21。[事前レビューで固定した焦点量](paired-rating-prior-review.md#6-次の費用パイロットで確認する量と判定案)を、保存済みの共同drawから計算する処理と、有限の実行予算を監視する処理を実装・検証しました。これは限定的な実装上の完了です。新しいMCMC、事前選定、回復・被覆・SBC、実データ分析は実施していません。

## 1. 今回答えた問い

次の推定で必要なのは、単に相関や予測を表示できることではなく、**報告したい量をどの数値精度で計算できたか、不十分なら何が不十分かを保存できること**です。未知録音では新たな録音効果を積分するため、その計算誤差と、元の事後標本が有限で依存していることによるMCMC誤差を区別する必要があります。また、費用上限を設計書に記載するだけでは、実行中の超過を止められません。

そこで既存の短い推定を再利用して、焦点量、チェーン構造、元の警告、積分精度の対応を確認しました。資源監視は、短時間のPython子プロセスを用い、実際の超過・割込み・監視不能を起こして確認しました。これらの検証は推定の統計的な妥当性を評価する研究とは役割が異なります。

| 基準別の全評価者対比 | 342 | 19評価者の全対、二基準。`rater[r,c]-rater[r',c]`。正なら第一の評価者の厳しさが大きい |

## 3. 未知録音の積分とMCMC誤差

未知録音の基準`c`に対する一つの評定確率は、各パラメータdrawで

```math
P(Y=k\mid q)=\int P_{\mathrm{PCM}}\{k\mid\eta_c(q)+\sigma_c(q)z,\delta_c(q)\}\phi(z)\,dz
```

と計算します。一つの基準の周辺確率では、その基準の録音SDだけが必要で、録音相関は積分から消えます。二基準や複数評定の**同時確率**では消えません。既存の共同予測処理は録音ごとに一つの二変量効果を共有し続けます。今回の周辺確率を掛け合わせて同時確率の代用にしません。

求積には、現在の依存環境にある[QuadGKの適応Gauss–Kronrod積分](https://juliamath.github.io/QuadGK.jl/stable/api/)を使います。私的な参照スクリプトからDistributionsが読み込む関数を利用し、コアの直接依存は追加していません。Julia 1.10/1.12の現環境で確認していますが、この私的な参照経路の将来互換性を公開契約とはしません。

カテゴリー確率と非自明な累積確率を同じベクトル積分で求め、最大成分誤差を用います。正規変数の区間`[-9,9]`を積分し、区間外は正規分布の尾確率による上界を記録します。カテゴリーのロジット直線が交わる点でも区間を分け、狭い確率の山を捉えやすくしています。許容値、評価回数上限、有限性、確率範囲、カテゴリー確率の和を検査し、不適合なdrawを落とさず計算を失敗として返します。

今回の指定は絶対許容値`1e-8`、各draw・各未知行につき最大10,000回の評価です。尾の上界と求積誤差の**推定値**を分けて考えます。適応求積が返す誤差推定値全体を、すべての入力に対する厳密な保証とは呼びません。独立したGauss–Hermite法、複合Simpson法、二値の対称性、極小・大きいSD、評価予算超過でも検証しました。

乱数による内側標本を加えないため、得られたdraw別周辺確率に既存のMCMC MCSE処理を適用できます。求積誤差推定値は別欄に残し、MCSEへ重ねて加算しません。以前の予測JSONの内側MCSEは、与えたパラメータdrawに条件付けた数値積分精度でした。今回のMCMC MCSEと意味が違います。現在の許容値は提案された平均確率精度0.01より十分小さいものの、任意に狭い事後区間の端の正確さまで一律に保証するものではありません。

## 4. 判定の条件と限界

計算上の適格性には、元の推定の診断、焦点量の診断、MCSEによる精度の三つを要求します。元の推定には4チェーン以上、適用対象の全パラメータと焦点量にはR-hat<1.01、bulk/tail ESS各400以上、さらに保持drawの発散・非有限密度0、チェーン別E-BFMI≥0.3を要求します。構造上固定された量だけは診断対象から区別し、動かなかった未知パラメータを固定値とはみなしません。[診断基準の位置付け](https://mc-stan.org/learn-stan/diagnostics-warnings.html)も参照してください。

対比・相関・SDの平均には`MCSE/事後SD≤0.05`、95%区間両端には`分位点MCSE/区間幅≤0.05`を使います。予測確率の平均は絶対MCSE≤0.01です。今回の実装では、予測確率にも区間を表示するため、**同じ区間端の条件を追加**しました。これは事前レビューの案を保守的に具体化した工学上の条件で、実用上の許容差を採用したものではありません。ゼロ幅の非定数量やMCSE未計算は通過扱いにしません。

診断とMCSEには既存のrank-normalized診断、平均MCSE、分位点MCSEを再利用します。個々のMCSEが利用できても、元の推定の診断不良を打ち消しません。木深さ上限到達は費用・効率の警告として保存し、それだけで偏りがあると断定する合否条件にはしません。結果には量別の`mcse_unavailable`、`precision_insufficient`、`precision_met`と、診断を合わせた`computationally_qualified`を別に保存します。全量が計算条件を満たした場合も、科学的受入は別です。

## 6. 時間・メモリ・出力の監視

[Python実装](../../scripts/paired_rating_resource_guard.py)は、POSIXと既存のpsutilを使い、argvで渡した信頼できるコマンドを専用プロセス群で起動します。シェル文字列、追加インストール、自動再試行は使いません。起動前に子プロセス情報とメモリ情報を取得できるか確認し、取得できなければ`observation_unavailable`を保存して起動しません。[psutilの仕様](https://psutil.io/api/)と[Pythonのプロセス起動仕様](https://docs.python.org/3/library/subprocess.html)を参照しています。

| 監視対象 | 実装上の扱い |
| --- | --- |
| 経過時間 | 単一コマンドの期限と、任意の共有monotonic期限の早い方。コンパイルをコマンド内で行う場合はその時間も含む |
| メモリ | 観測できた生存子孫のRSSを合算し、最大観測値を保存。共有ページを重複計上する場合がある |
| 出力 | 指定ツリーの通常ファイルの論理サイズを合算。コマンドログを含み、当該監視記録自身は除く。終了後も再計測する |
| 上限・監視不能・割込み | 専用プロセス群にTERMを送り、猶予後も残る場合はKILL。確認済みの子孫と終了状況を記録 |
| 親だけの終了 | 確認済みの子孫が生存していれば`unjoined_descendants`として終了処理を行う |
| 共有予算 | 二つ目の処理の前にも共有期限と総出力を確認。既存のジョブディレクトリは上書きしない |

一般的な利用形は次のとおりです。これは新しいパイロットの開始指示ではありません。

```text
python3 scripts/paired_rating_resource_guard.py \
  --directory <new-job-directory> --wall-seconds <seconds> \
  --rss-bytes <bytes> --output-bytes <bytes> --cwd <working-directory> \
  -- <executable> <arguments...>
```

バッチ全体の共有期限と出力ルートは、Pythonの`run_guarded(..., batch_deadline=..., output_root=...)`に明示します。将来のパイロットでは、コンパイル・各チェーンの出力をこのツリー内へ配置し、コンパイル開始前から共有時間を計測する呼出し側が必要です。コマンドが宣言外の場所に書くファイルは数えられません。

この処理はポーリング監視であり、OSによる厳密なメモリ・ディスク容量の割当制限ではありません。短いピークや親の終了に挟まれた未観測の子孫を見逃す可能性があります。既定では、観測済みの子が群を離れると監視不能として停止処理へ進みます。中核MGMFRMのCmdStan試運転用に追加した明示オプション `allow_descendant_groups=true` では、確認済みの別グループの子孫も同一性を追跡して計測・停止します。追加検査と実行結果は[中核候補の記録](mgmfrm-first-acceptance.md#乱数環境資源監視)にあります。観測間に分離して親子関係も失った未観測プロセス、権限変更、共有出力の外部変更、監視者自体のSIGKILL、OS停止、ストレージI/O停止まで扱う仕組みではありません。したがって8 GiB／2 GiB案は「超過を観測したら停止する閾値」であり、厳密な使用量上限の保証ではありません。

### 実際の検証と修正

通常サンドボックスではプロセス一覧の取得が拒否され、[起動前停止の記録](../../results/workflows/20260921-paired-precision-01/guard-default-01/default-sandbox/guard-receipt.json)が残りました。コマンドは起動されていません。監視機能を試すため、限定したPythonテストをプロセス情報の取得が許可された実行権限で実行しました。

最初の16テストでは7件失敗しました。TERM後の終了済みプロセス群に対する`killpg(...,0)`がEPERMを返し、終了確認を打ち切っていたためです。macOSの[公開XNU実装](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_sig.c)では、ゾンビを信号対象から除外し、対象がなければPOSIX経路でEPERMを返す場合があります。実測した例外箇所もこの挙動と整合します。修正では、EPERMだけを根拠に消滅したとはせず、群への所属と生存状態を確認するようにしました。情報取得が失敗した場合は成功に読み替えません。

修正後は**18テスト全通過**です。時間超過とTERM無視後のKILL、子孫のRSS合算、ファイル・ログの出力超過、最後の計測後の出力増加、親だけの終了、途中の観測失敗、起動前拒否、共有時間・出力予算、割込み、シンボリックリンク・読取失敗、上書き拒否、権限エラーとゾンビ群の回帰検証を含みます。各テストは自身が作ったPython子プロセスだけを対象とし、メモリ用データは最大80 MiBです。停止後に観測対象の生存プロセスは残りませんでした。[成功記録](../../results/workflows/20260921-paired-precision-01/guard-full-02/verification.json)と失敗した初回の記録を両方保持しています。他OSでの動作や長いMCMCジョブでの監視は未検証です。

## 7. ロードマップ上の位置

今回で「保存drawからの焦点精度評価」と「監視処理の限定検証」は完了です。次の律速点は、ステップ形状・尺度・相関階層が応用の問いに適切かという科学的判断と、その判断を反映したパイロットの実行契約です。

1. 中間カテゴリーにどの役割を期待するかを明確にし、現行事前を維持するか別の事前を定義するかを判断する。生成例への近さだけで採用しない。作成者の検討と独立レビューを区別する。
2. 採用するターゲット、事前、パイロット専用データ、焦点設計、コンパイルを含むコマンド・出力先、監視権限、総予算、停止条件を実行前に固定する。新しい事前なら正規化と両実装を先に検証する。
3. 合意した一組の合成データにJulia/CmdStan各1回、各4チェーン×(500 warmup＋500 retained)までという既存の費用パイロット案を、宣言した上限内で実施する。上限案は各30分・全体60分、群RSS8 GiB・総出力2 GiBで、自動延長・再試行は行わない。今回は未着手。
4. 得られた費用と焦点量の精度・失敗状況を基に、回復・被覆・事前感度・録音単位の予測評価の必要範囲と反復数を設計する。十分な精度が得られない条件も成果として報告する。

パッケージ全体の統計的受入、通常APIへの移行、全体CI、独立再現、初見利用者の確認、統合・リリースは別の未完了事項です。今回の検証件数を全体の完成率へ換算しません。
